# Спецификация бэкенда и интеграции React

**Цель на 48 часов** — автономная витрина, в которой покупатель получает конкретное предложение с ценой, может открыть варианты семейства и видит допродажу только после проверки совместимости. Spring Boot на Java 21 обслуживает React и публичный API на одном origin. Один экземпляр приложения читает неизменяемый каталог SQLite и индекс Lucene, а события пишет во второй файл SQLite. Лексический режим обеспечивает весь пользовательский сценарий. Локальный FastAPI добавляет векторный поиск при подтверждённом приросте качества.

Spring обслуживает поиск, подсказки и карточки из импортированного снимка SQLite/Lucene и сохраняет успешные поиски в `search_log`. Vite проксирует `/health` и `/v1`. Клиентские события и отчёт по сессиям описаны ниже для следующего этапа. [Запуск с каталогом](../README.md#поиск-по-каталогу-softline) Порт 8001 обслуживает документацию с примерами и возвращает `501 CONTRACT_ONLY`. Источник форматов HTTP — [OpenAPI витрины](../contracts/search.openapi.yaml) и [OpenAPI энкодера](../contracts/model.openapi.yaml). Точные имена, типы, допустимость NULL, ключи и индексы SQLite заданы в [DDL каталога](../contracts/sql/catalog-v1.sql) и [DDL событий](../contracts/sql/events-v2.sql).
Это целевая спецификация. Первый этап включает импорт снимка, лексический индекс, публичные маршруты `/v1`, журнал и отчёт. Порт 8001 обслуживает документацию с примерами и возвращает `501 CONTRACT_ONLY`. Источник форматов HTTP — [OpenAPI витрины](../contracts/search.openapi.yaml) и [OpenAPI энкодера](../contracts/model.openapi.yaml). Точные имена, типы, допустимость NULL, ключи и индексы SQLite заданы в [DDL каталога](../contracts/sql/catalog-v1.sql) и [DDL событий](../contracts/sql/events-v2.sql).

## 1. Один Java-модуль и две точки входа

Корневой пакет — `ru.codesraider.smartsearch`. Ниже указаны планируемые границы кода. Зависимости — Spring MVC/Validation, Spring JDBC с `JdbcTemplate`, Xerial SQLite JDBC, Lucene core/analysis-common/grouping, Spring `RestClient`. Версии сборки и профили Compose берутся из [технического плана](TECHNICAL_ARCHITECTURE.md).

| Пакет | Вход и ответственность | Результат |
|---|---|---|
| `catalog` | Команда `import` того же образа читает XML через StAX, словари и проверенные правила. В режиме сервера репозиторий разрешает `(kind,id)`, читает варианты семейств и связи пачками по ключам. | Новый снимок или данные строго одной активной версии. |
| `search` | MVC-обработчики поиска, подсказок и сущностей. Java records отражают DTO OpenAPI, Bean Validation и общий обработчик ошибок проверяют вход. Поисковый сервис разбирает запрос, получает кандидатов из Lucene, проверяет SKU и собирает ответ. | `SearchResponse`, список `Suggestion` или `Entity`. На каждый успешный POST поиска создаётся ровно одна запись в журнале, включая пустую выдачу. |
| `analytics` | Запись поисков, валидация вариантов событий, атомарная запись пакета, атрибуция и расчёт отчёта. Для чтения истории профиля используется тот же журнал. | `search_id`, подтверждение события или `AnalyticsResponse`. |
| `modelclient` | Внутренний HTTP-клиент к FastAPI. Сверяет профиль, размерность, число и качество векторов. Обслуживает запросы поиска и пакетный импорт. | Векторы либо явный переход к лексическому режиму. |

**Режим импорта.** Команда `docker compose run --rm --no-deps -v "/absolute/path/Mindbox.yml.gz.xml:/catalog.xml:ro" app import` читает `CATALOG_PATH`, доступный *в контейнере*. Подключить исходный XML только для чтения, том снимков для записи импортёром и отдельный постоянный том для журнала. Предлагаемая раскладка — `snapshots/<index_version>/{catalog.db,lucene/,manifest.json}`, указатель `snapshots/active`, файл `events/events.db`. StAX читает без внешнего DTD. Сначала собрать новую версию во временном каталоге на том же диске. В манифест записать версию, дату и SHA-256 выгрузки, версию схемы и словарей/правил, число предложений, семейств, векторов и `profile_id` при наличии. Закрыть писатели, проверить связи, счётчики и эталоны; только после этого атомарно заменить указатель и перезапустить приложение. Повторный импорт того же содержимого и конфигурации может переиспользовать проверенную версию. Для отката выбрать предыдущий снимок.

**Конфигурация стенда.** `APP_PORT` задаёт порт Spring на хосте (обычно 8080); `MODEL_BASE_URL=http://model:8000` доступен Spring внутри сети Compose. Для импорта с векторами использовать `import --embeddings` с прогретой моделью. Плановый `SEMANTIC_MODE=auto` включает гибридный путь только при совместимых векторах. При запуске лексического снимка веса и ключ LLM не требуются.

**Режим сервера.** При запуске прочитать указатель один раз и открыть соответствующие `catalog.db` в режиме read-only и Lucene `DirectoryReader`. Обработчик использует одну пару до конца запроса. Миграцию `events.db` применять отдельно по `PRAGMA user_version`, включать `foreign_keys=ON` и ограниченный `busy_timeout` на каждом соединении. История и заказы переживают замену каталога. Для готовности Spring нужны открытый снимок SQLite/Lucene и журнал событий, доступный для записи. `/actuator/health/readiness` возвращает `503` при отказе любой из этих зависимостей. `model_service` сообщает о доступности HTTP-процесса модели, `semantic_ready` — о совместимости прогретой модели и векторов активного снимка.

## 2. От XML до полей каталога

Схема предназначена для полного снимка, включая недоступные позиции и товары без цены. Идентификаторы и артикулы хранятся как текст. Отсутствующее значение — SQL NULL. Ноль цены в каталоге сохраняет исходное значение; на границе публичного API ноль и отсутствие цены превращаются в JSON `null`.

| Таблица | Источник и правила заполнения |
|---|---|
| `entity` | Справочник переходов. `entity_key` — внутренний PK, `(kind,id)` — уникальный публичный адрес; `name` — подпись. URL товара берётся из `offer/url`, вендора — из `vendorUrl`, канонические адреса семейств и подборок — из проверенного справочника. При пустом `canonical_url` вернуть путь к локальной React-карточке, например `/?kind=family&id=391338`. |
| `vendor`, `category`, `collection_scope` | `vendor_id` — ключ из пути `vendorUrl`, например `cyberprotect`. `category_id`, `parent_id` и имя категории берутся из дерева XML. У `collection/cyberprotect-1033` два обязательных условия на одной строке предложения — вендор `cyberprotect` и категория `1033`. Та же область действует для подсказки после выбора, свободного ввода, вариантов и дочерних переходов. |
| `offer` | `offer_id` ← `offer/@id`, `group_id` ← группа из XML, `available` ← `@available`, `sku_raw` ← `vendorCode`, `sku_norm` — ключ точного сопоставления. Пустой артикул → NULL; индекс по артикулу допускает повторы. Сохраняются исходные `name, url, description, sales_notes`, связи на вендора и категорию. `price, oldprice` переводятся десятичной арифметикой в целые минимальные единицы, `RUR` → `RUB`. |
| `offer_param` | Каждое вхождение `param` сохраняет исходные `name,value` и порядковый `ordinal` внутри SKU. `field_key,value_norm` позволяют искать подтверждённые нормализованные значения, включая несколько платформ или языков одного SKU. Для служебного текста «другое или отсутствует» сохраняется оригинал, нормализованное значение пустое. |
| `alias` | Нормализованный термин, целевая сущность и область применения. `*` — общий словарь; `category/{id}` — контекст раздела. Одинаковый текст может вести к нескольким сущностям. Словарь намерений связывает проверенные формулировки задачи с категориями и попадает в версию снимка. |
| `demo_signal` | Опциональные демонстрационные оценки популярности и маржи конкретного SKU в диапазоне 0–2, где 2 — максимальная. Источник — помеченный синтетический набор. Отсутствие записи для SKU означает отсутствие коммерческого сигнала. |
| `relation` | Направленная связь двух семейств. `rule_id,rule_version,source_url` фиксируют проверенное основание. `predicates_json` содержит обязательные сравнения конкретной пары SKU. Например, для Pantum — `[{"field":"supported_device","anchor_sku":"BM1800W","candidate_sku":"TL-C2318H","vendor_id":"pantum"}]`; для ПО — проверенные значения версии, платформы, редакции или типа лицензии с указанием стороны. Java поддерживает только известные типы правил. |

**Формат проверки связи.** Элементы `predicates_json` соединяются через AND. Для `supported_device` сверить точные нормализованные коды и вендора у обоих SKU. Для программного правила использовать пары подтверждённых значений, например `{"field":"compatible_versions","anchor_field":"version","anchor_equals":"1.8","candidate_field":"version","candidate_equals":"17.2"}`. Этот пример описывает проверку пары версий после отбора двух семейств; дополнительные предикаты отдельно фиксируют требуемые платформу, редакцию и лицензию. Разрешённые поля берутся из типизированных характеристик SKU. Совпали обе стороны — `pass`; доказанное противоречие — `fail`; пропуск, неоднозначность или неподдерживаемое правило — `unknown`. В возвращаемой проверке `anchor_value,candidate_value` — фактические значения, `source_url` — источник применённого правила.

**Три разных идентификатора.** У предложения есть запись `entity_key=offer/{offer_id}`. У ПО `family_key=family/{group_id}`, у подтверждённой модели оборудования — например `hardware/pantum/p2500w`. Оба ключа семейства указывают на `entity.kind=family`. У публичного аппаратного семейства хранить отдельный стабильный ID без косых черт (например `pantum~p2500w`). Клиент берёт ID из DTO цели. При раскрытии карточки из выдачи React открывает `GET /v1/entities/offer/{offer_id}`. Если у этого SKU есть другие подходящие варианты, Spring включает переход `{kind:"family",id,url}` в существующий массив `children`. React открывает этот ID с теми же фильтрами. Когда исходная подсказка или цель уже имеет тип `family`, достаточно одного запроса. Так клиент получает варианты и у ПО, и у аппаратных моделей без разбора `family_key`. У оборудования без подтверждённой модели `family_key=NULL`: точный переход к SKU доступен, место среди четырёх семейств требует подтверждённой группы.

**Характеристики и бюджет.** В `offer` хранить тип продукта, базовую модель, версию, редакцию, `license_type=new|renewal|upgrade` и срок в месяцах. «Подписка» сама по себе не подтверждает продление. `device_count,seat_count` — фиксированное покрытие пакета; `device_min/max,seat_min/max` — подтверждённые границы выбираемого количества. Пропуск границы означает неизвестное условие, если источник не подтверждает открытый диапазон. `min_order_qty` — отдельный минимум закупки в единицах продажи. В `fact_sources_json` указать источник каждого извлечённого свойства, например `{"term_months":{"param_ordinal":2}}`; для открытой границы явно отметить это в источнике. Название семейства не доказывает версию конкретной лицензии.

Для бюджета сравнивать валюту и полную стоимость. При цене за устройство/место количество единиц покупки должно покрывать запрос и минимум закупки. Для пакета брать цену целого пакета; умножать число пакетов можно лишь при подтверждённой возможности сложения лицензий. Если единица продажи, обязательное покрытие или итоговая стоимость неизвестны, бюджетное условие не пройдено. В `Offer.price_minor` отдаётся цена самого предложения из снимка. Акцию показывать только при `available && old_price_minor > price_minor > 0`.

## 3. Lucene и порядок работы обработчика

| Тип документа | Индексируемые поля и назначение |
|---|---|
| `offer` | Точные поля типа документа, `offer_id,sku_norm,family_key,vendor_id,category_id`, базовая модель и фасеты. Отдельные текстовые поля для семейства, названия, вендора, пути категории, характеристик и описания. Русский анализатор для описаний; бренды, коды и цифры сохраняют точный вариант. `SortedDocValuesField(family_key)` для группировки. |
| `entity` | Тип, публичный ID, ключ, точное и префиксное имя, алиасы. По этим полям работают навигация и подсказки. |
| Семантический документ при включённом E5 | Один вектор на семейство ПО или на аппаратный SKU, с ключом для последующей группировки. `KnnFloatVectorField`, 384 float32, L2-нормализация и `DOT_PRODUCT`. Жёсткие условия окончательно проверяются на конкретном SKU в SQLite. Метаданные семейного вектора могут описывать несколько SKU; отсутствие фасета на этом документе само по себе не исключает семейство с подходящим вариантом. |

1. Разрешить `selected_target` в выбранном снимке. При свободном вводе сначала проверить ID и точный артикул. Для повторяющегося артикула сохранить кандидатов, проверить ограничения, затем выбрать представителя. Единственный точный SKU сохраняет собственный переход и фактический статус.
2. Нормализовать регистр, раскладку, дефисы, транслит и проверенные алиасы, сохраняя модель, артикул и цифры версии. Выделить назначение, явные включения, отрицания, альтернативы «или» и ограничения лицензии. Пересечь текстовые условия, область выбранной цели и `filters`. Два демонстрационных профиля в версионированном словаре связывают `profile_id` с предпочтительными типами товара и категориями. Для известной сессии последние товарные клики дают контекст по её истории; при смене снимка учитывать только разрешимые ID. Контекст, сессия и профиль помогают разрешить неоднозначность. Обязательные условия действуют при любом профиле.
3. Взять BM25-кандидатов до 100 разных семейств; начальные веса полей в порядке таблицы технического плана — 8, 6, 4, 3, 2, 1. Для запроса по задаче при готовой модели параллельно получить до 50 векторных соседей. В каждом списке свернуть совпадения по `family_key`, заново присвоить ранги от 1, сложить вклады `1/(60+rank)` по спискам. При равной релевантности использовать совпадение с контекстом, затем доступные демонстрационные оценки популярности и маржи и стабильный ключ. В MVP отсутствие коммерческого сигнала даёт нейтральную добавку 0. На «сервер» явное назначение и тип товара имеют приоритет перед этими поправками. Подсказки и точный SKU обходят энкодер.
4. Пакетно получить SKU семейств, применить все обязательные характеристики к **одному предложению**. В области прямых результатов использовать первую непустую очередь: доступные с ценой → недоступные с ценой → без подтверждённой цены. Проверить существование более высокой очереди за границей начального top-k. Внутри очереди выбрать представителя каждого семейства по релевантности; при полном равенстве — по стабильному ID. `available_only=true` отсекает недоступные SKU во всех очередях.
5. Сначала положить в `top4` разные прямые семейства. При свободных местах взять кандидатов из `relation` для уже показанных SKU. Каждое обязательное сравнение получает `pass|fail|unknown`; дополнение допускается только при всех `pass`, по своей очереди цены, из нового семейства и с `anchor_offer_id` показанного устройства/лицензии. Проверки с источниками вернуть в `checks`; причины исключений сохранить в диагностике. При нуле прямых совпадений оставить `top4=[]`, найденный функциональный аналог сразу вернуть в `alternatives` с отличиями и проверенными обязательными свойствами.
6. Сформировать ответ, зарегистрировать поиск и показанный состав одной транзакцией до возврата `200`. `direct_count` считает подходящие прямые семейства в рассмотренном пуле после фильтров и выбора очереди, до `limit`. Журналирование поисков выполняет Spring; событие браузерного показа привязано к фактической отрисовке. При ошибке фиксации обработчик завершает запрос ошибкой в общем формате Problem Details; клиент не получает успешного `search_id` для отсутствующей записи.

**Граница FastAPI.** Spring проверяет `GET /ready`; фоновая проверка отдельно от поискового запроса. В `POST /internal/v1/embeddings` передаются `input_type,profile_id,texts`: один текст для `query`, 1–32 для `passage`. FastAPI добавляет префикс и возвращает `profile_id,dimension,vectors` в исходном порядке. Перед использованием проверить профиль активного индекса, размерность 384, конечность и норму вектора. Стартовый бюджет онлайн-вызова — 200 мс в общем p95 поиска до 500 мс. При тайм-ауте, перегрузке или несовместимости профиля результат строится лексически. Профиль `ml` нужен только для измеренного гибридного режима. [Контракт и критерии подключения](FASTAPI_RETRIEVAL_HANDOFF.md)

## 4. Публичный API для React

Базовый URL — текущий origin, локально `http://localhost:8080`. В dev-профиле добавить в Vite proxy для `/v1` к тому же Spring, что и `/health`. JSON в UTF-8, ключи в snake_case. Все ID и версии — строки. Тип цели везде один из `offer, family, vendor, category, collection`. Для точных обязательных полей, примеров тел и схем разных событий использовать [публичную OpenAPI](../contracts/search.openapi.yaml); ниже описаны решения клиента при каждом ответе.

| Вызов | Что отправляет React | Как обработать успех |
|---|---|---|
| `GET /v1/suggest` | Query: обязательный непустой `q`, опционально `category_id` | `200` и массив до 6 элементов `{kind,target_id,label}`, включая пустой массив. Отменять устаревший запрос и проверять актуальность ответа. |
| `POST /v1/search` | JSON с обязательным непустым `q`. Опциональные `session_id, context, filters, selected_target, limit`. `limit` по умолчанию 4, диапазон 4–50. | `200 SearchResponse`. Сохранить `search_id` именно отображаемого ответа. При клике или Enter на подсказке отправить один POST с исходным префиксом и `selected_target={kind,target_id}`. При свободном вводе опустить `selected_target`. |
| `GET /v1/entities/{kind}/{id}` | Тип и публичный ID; непустые применимые фильтры передать плоскими query-параметрами через `URLSearchParams`. | `200 {kind,id,name,url,offers,children}`. Для семейства показать варианты, для предложения — выбранный SKU, для навигации — дочерние цели `{kind,id,url}`. Известная сущность после фильтрации может содержать два пустых массива. |
| `POST /v1/events` | Непустой JSON-массив типизированных событий. | `204` без тела. Повторять доставку с тем же `event_id` у каждой строки. |
| `GET /v1/analytics` | Обязательные `from,to` в RFC 3339 со смещением; `from < to`. Опциональные `source=demo\|seed`, `index_version`. | `200` с `period,zero_result_rate,abandonment_rate,conversion_rate,failures`. Состав метрик ниже. |
| `GET /health` | Без параметров. | `200 {status,model_service}`; `index_version,search_ready,semantic_ready` опциональны. Клиент стартового каркаса допускает их отсутствие. |

**Вложенные поля поиска.** У `context` есть опциональные `category_id,segment,profile_id`. У `filters` текстовые `category_id,vendor_id,platform,version`, перечисление `license_type`, положительные целые `term_months,device_count,seat_count`, boolean `available_only=false`, неотрицательный целый `max_price_minor` и трёхбуквенная `currency="RUB"`. Условия `filters` обязательны для кандидата; JSON-ключи этих условий опциональны для клиента. Для конфликтующего фильтра известной подборки вернуть явно запрошенное значение в `applied_filters`, сохранить цель и показать пустой результат.

**Ответ поиска.** Обязательные поля — `search_id,index_version,mode,normalized_q,applied_filters,primary_target,direct_count,top4,more_results,alternatives,upsell,shortfall_reason`. Возможные `mode` — `lexical` и `hybrid`. `primary_target` — `{kind,id,url}` или `null`. Отобразить массивы в порядке сервера. В `top4` до четырёх карточек, в `more_results` — только дополнительные прямые; сумма длин ограничена `limit`. Навигация и аналоги отображаются отдельными блоками. При четырёх позициях причина недобора `null`; при нуле прямых — `NO_DIRECT_MATCH`, иначе при неполной четвёрке — `NOT_ENOUGH_VERIFIED_FAMILIES`.

В `upsell` до восьми карточек. Сервер подбирает подтверждённые дополнения и похожие предложения из категории найденного товара или аналога. Совместимое дополнение может также присутствовать в `top4`. Клиент показывает один экземпляр и передаёт его позицию в `upsell`. Счётчик `direct_count` учитывает прямые совпадения.

| Данные карточки | Обработка в интерфейсе |
|---|---|
| `offer_id,sku,name,vendor,url,available,price_minor,currency,offer_tier` | Обязательные ключи. `sku` и `price_minor` могут быть `null`. Для RUB форматировать копейки как рубли; при `null` вывести «Цена не указана». Наличие берётся из `available`. `offer_tier=primary\|reserve`. |
| `old_price_minor,attributes` | Опциональны. `attributes` — объект с массивом строк на каждое свойство. Промо требует подтверждённого сравнения цен и наличия. |
| `family_key,reason_codes,role` | Поля карточки в поисковой выдаче; в `Entity.offers` возвращаются обычные `Offer`. `reason_codes` непустой. Учитывать роль каждого товара при клике. |
| `role=related` | Предложение в `upsell`. `catalog_pick` — похожий товар из категории, `curated_fallback` — редакционная подборка для ввода из знаков и символов. Поле `recommendation_reason` объясняет подбор. |
| `role=complement` | Дополнительно обязательны `anchor_offer_id` и непустые `checks[]` с `field,anchor_value,candidate_value,source_url,result="pass"`. |
| `role=alternative` | Обязателен непустой список `differences[]`. При пустой прямой выдаче всё равно отобразить аналог из этого же ответа. |

**Ошибки.** Тело — `application/problem+json` с `type,title,status,detail,code`. `400 INVALID_REQUEST` — исправить ввод; `400 UNKNOWN_TARGET` — сбросить устаревший выбор и обновить подсказки; `404 ENTITY_NOT_FOUND` — карточка отсутствует в снимке; `503 CATALOG_UNAVAILABLE` — поиск/каталог временно недоступен; `503 EVENT_STORE_UNAVAILABLE` у событий и отчёта — повторить доставку/загрузку позже. Пустая выдача — успешный поиск. Для остальных ошибок показать состояние ошибки по статусу. Падение одного энкодера при готовом каталоге видно по `mode="lexical"`, пользователь получает результаты.

## 5. События, атрибуция и расчёт отчёта

У каждого клиентского события обязательны строковые `event_id,session_id`, `ts` со смещением и `type`. `source` по умолчанию `demo`. Браузер повторно использует анонимный ID активной сессии и создаёт новый после 30 минут бездействия. Живой поиск получает `source=demo` на сервере; подготовленные поиски и события создавать согласованно с `source=seed` при локальной загрузке демоданных.

| Событие | Дополнительные поля |
|---|---|
| `impression` или `click` карточки | `search_id,offer_id,family_key,role,block,position`. Блок — `top4,more_results,alternatives,upsell`; позиция с 1 внутри блока. |
| `click` из деталей | `block=details,search_id,offer_id,family_key`. Указать фактически выбранный вариант. |
| `click` по цели | `block=navigation,search_id,target_kind,target_id`. |
| `reformulation` | `search_id` исходного и `next_search_id` нового уже выполненного поиска. |
| `add_to_cart` | `offer_id` обязателен; `search_id` может отсутствовать или быть `null`. |
| `order` | Одна товарная позиция на событие, обязателен `offer_id`. Входной `search_id` контракт заказа не принимает. |

**Что записывает Spring.** В `search_log` хранятся ID, время, источник и сессия, исходный и нормализованный запрос, пара полей выбранной подсказки, контекст и применённые фильтры, число прямых и показанных в top4 семейств, недобор, режим, версия индекса и длительность. В `shown_json` сохранить навигационную цель и упорядоченные блоки с ID, семейством, ролью и якорем. В `diagnostics_json` — основания отбора и отклонения, включая ID и версию правила, значения, источник и исход проверки пары. Незапрошенная сессия хранится как NULL: поиск участвует в метрике нулевой выдачи. Для сессионных метрик использовать установленную сессию; для интеграции React передаёт один `session_id` от поиска до заказа.

В `event` один PK на доставленное событие. Столбцы, применимые только к другой разновидности события, остаются NULL. Для событий брать момент действия из входного `ts`, для поиска — момент обработки Spring. Хранить все `ts` в обеих таблицах журнала как строки **единого UTC-формата** с девятью знаками дробной секунды и суффиксом Z для корректного сравнения времён в SQLite. Ссылки событий ведут на поиски в той же базе; ссылка на `offer_id` историческая, смена каталога не удаляет событие. Java сверяет ID поисков с источником и известной сессией; для клика из деталей учитывает выбранный вариант, для карточки — блок, роль и позицию из сохранённого ответа. Java сначала валидирует весь пакет по вариантам DTO, затем пишет в одной транзакции. Для повтора применяется `ON CONFLICT(event_id) DO NOTHING`; первая запись сохраняется. Ошибка в новой строке откатывает весь пакет.

**Как найти заказ.** У позиции заказа найти последний предшествующий товарный `click` с теми же `source,session_id,offer_id` и заполненным `search_id`; порядок — `ts DESC,event_id DESC`. Навигационный клик и клик по другому SKU того же семейства пропускаются. Полученный ID записать в `event.search_id`, при отсутствии клика — NULL. При доставке клика с опозданием пересчитать затронутые последующие заказы этой тройки в той же транзакции. При подсчёте конверсии учитывать одну сессию один раз независимо от количества заказов.

**Период и знаменатели.** Выбирать поиски по `search_log.ts ∈ [from,to)` и фильтрам отчёта. Для сессионных метрик взять различные пары `(source,session_id)` из выбранных поисков. Историю действий такой сессии читать до её завершения, включая события после правой границы периода; при фильтре версии засчитывать конверсию по заказу, атрибутированному выбранному поиску. Это принятое для прототипа правило когорт, чтобы запрос перед полуночью и последующий заказ сохраняли связь.

| Метрика | Числитель | Знаменатель |
|---|---|---|
| `zero_result_rate` | Поиски с `direct_count=0`, включая показ аналога | Все отобранные поиски |
| `abandonment_rate` | Завершённые неуспешные сессии без дальнейшего клика или заказа после последней неудачи | Сессии с неуспешным поиском, завершённые после 30 минут бездействия |
| `conversion_rate` | Сессии хотя бы с одной атрибутированной позицией заказа | Все выбранные поисковые сессии |

Для реализации MVP неудачный поиск для знаменателя ухода — запрос с нулём прямых совпадений. Положительную выдачу с последующей переформулировкой анализировать отдельно в отчёте причин. `Metric={numerator,denominator,value}`, при нулевом знаменателе `value=null`. У `failures[]` поля `reason,count,query_examples,action`; использовать только `missing_synonym,ranking,catalog_gap,unavailable,filter_conflict,unknown`. Для группировки выбирать одну основную причину на поиск по диагностике и действиям пользователя. «Нет в каталоге» остаётся гипотезой для проверки менеджером.

## 6. Очерёдность реализации и приёмка

| Часы по плану | Что можно принять |
|---|---|
| 0–4 | DTO согласованы с OpenAPI; схемы SQL применяются к пустым файлам; импортёр читает полный XML; React умеет различать пустой ответ, недобор и ошибку. |
| 4–12 | Работают лексический поиск, точный SKU, семейство и журнал. `EP2-06605` ведёт к предложению `473582`, цена `3658400` копеек. Клик виден в SQLite. |
| 12–20 | Подсказка и свободный ввод ведут к одной цели, работают обязательные фильтры, профили, нормализация и проверки пары SKU. |
| 20–28 | На четырёх изолированных фикстурах проходит [HTTP-приёмка Spring](SEARCH_API.md#приёмка-поискового-обработчика-spring). Для «Кибер Бэкап» проверить область 1033, конфликт фильтра и резерв. Для Pantum — две модели, две верные пары, исключение картриджа без кода и немедленный аналог отсутствующей модели. На полном снимке проверить 8 продуктовых эталонов и 2 навигационных. |
| 28–34 | Только при готовом ядре сравнить BM25 и BM25+E5. Подключить E5 при приросте nDCG@4 на запросах-задачах ≥0,05, сохранении FamilyHit@4, точных SKU, навигации и p95 ≤500 мс. |
| 34–48 | Проверить атрибуцию конкретного SKU, повтор доставки, отчёт по неудачам, рестарт без модели и сохранность событий после отката. Заморозить сборку по [графику сдачи](HACKATHON_PLAN.md). |

Детальные примеры HTTP-запросов для React, ошибок и событий доступны в [руководстве по API](SEARCH_API.md). Базовый показ требует Java, React, Lucene и двух файлов SQLite. Отдельный экран менеджера и эксперимент с внешней LLM остаются следующими по приоритету после обязательного поиска, допродаж и отчёта.
