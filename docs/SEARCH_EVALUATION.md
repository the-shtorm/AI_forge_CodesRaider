# Проверка поиска Softline на демонстрационном каталоге

## Что требовалось от поиска

Покупателю нужен правильный первый переход и до четырёх разных семейств с проверяемыми условиями конкретного предложения. Заказчик допускает заполнить свободные места проверенными допродажами. Аналог отсутствующей модели нужно показать в первом ответе и объяснить различия. Excel задаёт восемь переходов к семействам, один к вендору и один к подборке. Исходный коммит `b155a3a` содержал Spring-каркас с `/health`, Swagger с примерами и приёмочные тесты для будущего обработчика. [Техническое задание](../supplementary/Technical_details_smart_search.pdf) · [Уточнения заказчика](../supplementary/userQnA.md) · [Excel](../supplementary/SearchQueries.xlsx)

## Как устроен метод

В XERJ модель переводит вопрос в короткую программу над типизированными записями. Результат вычисляет исполнитель, который может проверить обращения к фактам. Авторы в исправлении к статье описывают различия в условиях своего эксперимента. Для Softline заимствован этот принцип. Использованы местный каталог, Lucene и Qwen2.5-1.5B-Instruct Q4_K_M. Числа в этом отчёте измерены на поиске Softline. [XERJ Query-1](https://xerj.org/blog/xerj-query-ai-model) · [Модель Qwen](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF/tree/91cad51170dc346986eccefdc2dd33a9da36ead9)

1. **Подготовка данных.** При старте Spring потоково читает YML, сохраняет повторяющиеся параметры SKU, нормализует коды, валюту и цену в копейках. Строятся Lucene BM25 по названию, атрибутам и тексту, точные индексы предложений и списки для семейств, категорий, вендоров и поддерживаемых назначений. Для прототипа каталог и индекс живут в памяти процесса. В SQLite на постоянном томе сохраняются запрос, версия снимка, программа и показанные карточки. [Каталог](../backend/src/main/java/ru/codesraider/smartsearch/search/Catalog.java) · [Журнал](../backend/src/main/java/ru/codesraider/smartsearch/search/SearchJournal.java)
2. **Понимание запроса.** ID и артикул, выбранная подсказка, известные имена и однозначные назначения обрабатываются локально. Правила разбирают бюджет, версию, срок, количество, платформу, тип лицензии и поддерживаемые отрицания. Для свободных запросов слова покупателя ограничивают множество допустимых операций модели. При одном назначении модель возвращает один оператор. Для составного запроса схема допускает два различных поиска с пересечением или объединением. Например, для вебинаров или удалённого доступа исполнитель может объединить два списка SKU. Неверная структура, неизвестная инструкция, исчерпание времени или занятые слоты вызывают переход к лексическому поиску. [Компилятор](../backend/src/main/java/ru/codesraider/smartsearch/search/QueryPlan.java) · [Клиент модели](../backend/src/main/java/ru/codesraider/smartsearch/search/ModelClient.java)
3. **Исполнение.** Все обязательные условия проверяются у одного SKU. Цена сравнивается в валюте бюджета с учётом известной единицы продажи. Затем исполнитель выбирает доступные предложения с ценой, при их отсутствии переходит к ценовому резерву, а после него к резерву без цены. В выдачу попадает один представитель семейства. Для Pantum проверяются вендор и точные коды устройства и расходника. Карточка дополнения сохраняет ID показанного устройства и URL производителя. Для отсутствующего P2507 отдельно проверяются характеристики аналога. [Исполнитель](../backend/src/main/java/ru/codesraider/smartsearch/search/SearchEngine.java) · [Проверки условий](../backend/src/main/java/ru/codesraider/smartsearch/search/Requirements.java)
4. **Пояснение.** В основной выдаче сразу видна причина показа. Кнопка «Почему этот товар?» обращается к `POST /v1/explain`. Сервер загружает именно показанный SKU из сохранённой выдачи. Модель выбирает из подтверждённых фактов деталь для покупателя. Сервер собирает фразу и подставляет ссылку на карточку или проверенную пару. В ответе видны выбранные основания и источник текста — `llm` либо `template`. Пояснение запрашивается отдельно и не входит в задержку поиска. [Контракт API](../contracts/search.openapi.yaml)

## Эксперимент

Снимок включает **35 предложений**. Часть ID, цен и URL взята из контрактных примеров проекта. В него также добавлены тестовые варианты лицензий, цены, параметры и отвлекающие товары. Например, один SKU семейства CSP имеет версию 4.0, другой — 5.0. Все режимы получили один снимок целиком. Компилятор получает запрос и схему разрешённых инструкций. Эталонные ответы доступны только скрипту оценки. [XML](../backend/src/main/resources/search/demo.xml) · [Исходные примеры](../model/search_contract/examples.py)

**70 запросов** включают 10 из Excel и 60 ручных проверок. В 57 запросах есть размеченный прямой ответ, в 13 ожидается пустая прямая выдача. В разметке перечислены допустимые SKU. Несколько равнозначных предложений одного семейства засчитываются один раз. Для существующего товара Hit@4 означает хотя бы один релевантный прямой результат. nDCG@4 с бинарной релевантностью учитывает и позицию, и число подходящих семейств. Проверки пустой выдачи, навигации, расходников и аналогов считаются отдельно. [Разметка](../backend/acceptance/judgments.tsv) · [Скрипт](../backend/acceptance/benchmark.py)

Сравнивались три режима. Базовый SQLite FTS5/BM25 ищет по названию и описанию, допускает совпадение любого токена, выбирает доступные товары с положительной ценой и сворачивает семейства. Это воспроизводимая вариация эксперимента из репозитория. Второй режим использует Lucene, нормализацию и тот же исполнитель со всеми правилами при отключённой модели. Третий добавляет модель к этому же коду. Qwen работает в llama.cpp с четырьмя потоками CPU. Для двух HTTP-режимов каждый запрос отправлен трижды последовательно. Качество считается по первой выдаче, p50 и p95 — по всем 210 запросам каждого режима, включая HTTP и запись журнала. Повторы могут использовать кэш префикса llama.cpp. Время SQLite измеряется внутри процесса Python и с HTTP-временем напрямую не сравнивается. [Исходное исследование](../RESEARCH.md)

| Метрика | SQLite BM25 | Правила + Lucene | Правила + Lucene + Qwen |
|---|---:|---:|---:|
| Подходящий SKU на первом месте, 57 положительных запросов | 21/57 | 46/57 | 52/57 |
| Подходящий SKU среди первых четырёх, 57 положительных запросов | 22/57 | 46/57 | 52/57 |
| Средний nDCG@4 на этих запросах | 0,358 | 0,807 | 0,912 |
| nDCG@4 на 10 описаниях покупательских задач | 0,000 | 0,700 | 1,000 |
| Правильный пустой прямой ответ | 4/13 | 13/13 | 13/13 |
| Семейство из Excel среди прямых карточек | 7/8 | 8/8 | 8/8 |
| Точный первый URL из Excel | 0/10 | 10/10 | 10/10 |
| HTTP p50 / p95, мс | — | 8,45 / 15,83 | 8,98 / 864,41 |

В базовом варианте первый URL всегда ведёт на SKU, что объясняет 0/10 переходов к семействам и подборкам при 7/8 попаданиях в семейство. Результаты по каждому запросу содержат ожидаемые и возвращённые ID, источник программы и три измерения времени живых HTTP-режимов. [Результаты CSV](../backend/acceptance/benchmark-results.csv)

## Что показали проверки

По Hit@4 получено **+30 запросов из 57** к BM25, или **+52,6 процентного пункта**. Из них 24 добавило сочетание правил, индексов и группировки, ещё 6 — подключение модели. На первых прогонах 62 из 70 запросов обслужили правила, в 6 случаях был принят план Qwen, по одному разу модель отказалась и сработал резервный поиск после неприемлемого плана. Все три повтора дали одинаковые списки прямых ID для каждого запроса.

По запросу «сервер» возвращаются 4 модели оборудования. «ПО для сервера» поднимает лицензии для сервера, в том числе Кибер Бэкап и Windows Server. Для «Нужны вебинары или удаленный доступ» есть 5 прямых семейств, первые четыре занимают места в основной выдаче. Для «Кибер Бэкап версии 17.2» версий у предложений в снимке недостаточно и прямых совпадений нет.

Пять положительных запросов остались без прямого результата. Среди них артикул внутри фразы «Наш бухгалтер хочет купить EP2-06605», смешанная кириллица и латиница в «мicrosoft 365 для семьи», описание управления чужим экраном, защита от троянов и составная задача с приглашениями на видеоконференцию. На сложной подвыборке `challenge` модель дала попадание в 4 из 9 положительных случаев. На десяти более прямых описаниях назначения из подвыборки `task` получено 10/10. Эти две цифры показывают чувствительность результата к формулировкам.

Проверка уложилась в целевые 500 мс p95 в режиме правил. С активным компилятором p95 составил **864 мс**, хотя медиана осталась меньше 10 мс. Ограниченный набор операций и проверка SKU защищают факты карточки. Ошибка в интерпретации естественного языка по-прежнему может выбрать неподходящее назначение. В обоих режимах поиска полезна раздельная диагностика компиляции, исполнения и пустой выдачи.

При разработке обнаружились две разные ошибки генерации. Модель могла дописать второй поиск к одному запросу или отнести посторонний предмет к резервному копированию. Размер программы теперь ограничивается формой запроса, а допустимые операции требуют признака назначения в пользовательском тексте. В отдельном тесте запрос с неизвестным оператором переходит к лексическому пути. Также исправлены обработка копеек и групп разрядов в бюджете, кириллические границы слова «сервер» и поиск расходника по сочетанию вендора и артикула.

Обращение за объяснением нельзя использовать для подмены показанного предложения. Проверки покрывают отсутствующий в выдаче ID, выбор разрешённого факта и возврат к шаблону при некорректной генерации. В живом прогоне Qwen объяснила 4 из 4 показанных карточек Pantum за 1,76–3,70 с на карточку. Для обоих расходников выбрана проверенная пара устройства и артикула. В отдельной попытке при занятом CPU первое пояснение перешло к шаблону после таймаута 5 с. Для поиска прошли 7 модульных регрессий и 24 HTTP-проверки на четырёх вариантах фида, а также 5 существующих Python-тестов контрактов. В Chromium пройден путь из подсказки к подборке, затем поиск двух принтеров, открытие пояснения, пустая выдача и переход к локальной карточке. [JUnit для программы](../backend/src/test/java/ru/codesraider/smartsearch/search/ProgramTest.java) · [HTTP-приёмка](../backend/src/test/java/ru/codesraider/smartsearch/SearchHandlerIT.java)

## Границы результата

Восемь семейств и два навигационных перехода из Excel известны заранее и входят в справочник. Попадание в Excel подтверждает корректность интеграции. Дополнительные проверки составлялись внутри проекта и использовались для исправления ошибок. Оценка на полном фиде и слепая проверка с покупателями остаются открытыми. В частности, при подключении фида нужно сверить реальные имена параметров версий, единиц покупки и диапазонов лицензирования. Версия ПО у неопределённого SKU не доказывает совместимость с Astra Linux.

Рабочий путь покрывает поиск, подсказки, пояснения, сохранение выдачи и контекст текущей категории. Сессионная персонализация, коммерческие сигналы, приём событий корзины и заказов и бизнес-дашборд относятся к общему плану команды. Для оценки конверсии и эффекта допродаж нужны действия покупателей. В измеренном локальном режиме нет тарифа генеративного API. Денежная стоимость запроса требует цены вычислительного узла, срока его работы и объёма трафика.

## Условия сборки в проверочном окружении

Контейнеры работали через сетевой прокси. Для сборки исходников сертификаты окружения и настройки Maven были временно переданы в BuildKit. Исходный Compose healthcheck Spring может отправить локальный запрос через прокси и получить HTTP 403 при работающем приложении. Проверено обращением к одному и тому же URL из контейнера. При указании `wget -Y off` проверка возвращает `UP`. На время проверки стенда это изменение применялось локальным наложением Compose.

## Как повторить

Скачать веса и сверить контрольную сумму можно по инструкции запуска. Затем поднять два экземпляра на разных портах и выполнить скрипт из корня репозитория. Для скрипта достаточно Python 3 с SQLite FTS5. [Запуск витрины](../README.md)

```sh
APP_PORT=8081 docker compose -p search-rules up --build -d app
APP_PORT=8082 docker compose -p search-llm -f compose.yaml -f compose.llm.yaml up --build -d app
python backend/acceptance/benchmark.py --rules http://localhost:8081 --model http://localhost:8082 --repeat 3 --csv /tmp/softline-search.csv
```

Для HTTP-приёмки генератор строит четыре изолированных XML. Для каждого файла запустите приложение с соответствующим `CATALOG_PATH` и выполните профиль `search-acceptance`, передав имя сценария. В Docker используйте переменные монтирования каталога из README. [Процедура и ожидаемые результаты](SEARCH_API.md#приёмка-поискового-обработчика-spring)

```sh
python backend/acceptance/build_fixtures.py backend/src/main/resources/search/demo.xml /tmp/softline-fixtures
cd backend
./mvnw test
./mvnw -Psearch-acceptance -Dsearch.baseUrl=http://localhost:8080 -Dsearch.scenario=baseline verify
```
