# Умный поиск для Softline Store

**План на 48 часов · 26–28 ноября 2026 · трек «Аналитик данных»**

К сдаче покупатель должен уметь найти продукт по задаче, названию или артикулу, выбрать подходящую лицензию и понять, почему её предложили. Сотрудник магазина должен увидеть, какой спрос поиск обслужил и где покупатель ушёл без подходящего товара. Обязательный результат — витрина, поисковый API, журнал запросов и разбор неудач. Отдельный экран аналитики принесёт бонус. Данные — предоставленный снимок каталога и явно помеченные демонстрационные события.

**Главный выбор для команды.** Сначала собрать поиск по товарным семействам и конкретным предложениям. Включить компактную локальную модель эмбеддингов, только если она улучшит поиск по описанию задачи на независимых запросах. Внешнюю генеративную модель команда рассматривает как отдельный эксперимент. Базовый сценарий работает локально.

**Стек реализации — Java 21 и Spring Boot, React на JavaScript, FastAPI для локальной модели.** Библиотеки, HTTP-контракты, схема индексов, ресурсы и задачи по ролям собраны в [техническом плане реализации](TECHNICAL_ARCHITECTURE.md).

## 3. Как обрабатывать запрос

**Индекс.** Spring Boot использует встроенный Apache Lucene для BM25, префиксных подсказок и векторного поиска. Таблицы SQLite хранят предложения, семейства, вендоров, категории, атрибуты и канонические URL. Второй файл SQLite хранит события при замене индекса. Spring отдаёт сборку React и публичный API. Внутренний FastAPI кодирует тексты для семантического режима. На стенде всё запускается через Docker Compose. [Apache Lucene](https://lucene.apache.org/core/)

1. **Импортировать и восстановить иерархию.** Потоково разобрать XML. Сохранить исходные названия, `offer_id`, `group_id`, `vendorCode`, `vendorUrl`, URL предложения, доступность, цену, старую цену, `sales_notes`, путь категории и все повторяющиеся `param`. Преобразовать длительность в месяцы, количество мест и узлов — в числа или интервалы с единицей. Служебные значения «не определено» и «другое или отсутствует» заменить пропусками. Условия минимальной закупки учитывать отдельно от числа устройств. В споре между общим названием семейства и явной версией SKU побеждают данные SKU. Новую версию индекса строить рядом и переключать после сверки счётчиков и эталонов.
2. **Сохранить исходный запрос и разобрать его.** Точное совпадение с артикулом или ID искать до преобразований. Затем привести регистр, пробелы, варианты дефисов и «ё/е». Сделать дополнительные варианты для неверной раскладки, транслита, морфологии и проверенного отраслевого словаря. Примеры — «антивирь», «винда», «астра линукс», «мдаемон», «max patrol». Исходное написание остаётся одним из кандидатов. Числа, версии, короткие коды и артикулы защищены от нечёткого исправления. Исправление слова предлагать по словарю каталога при достаточном перевесе и показывать в интерфейсе.
3. **Выделить намерение и ограничения.** Различать артикул, семейство, вендора, категорию и описание задачи. Извлекать явные условия — новое приобретение или продление, ОС, версия, срок, число устройств, сегмент, тип товара, бюджет. Хранить источник признака. Явную несовместимость исключать. Когда обязательное свойство неизвестно, товар можно показать отдельно для уточнения. «На 5 ПК» допускает покрывающий диапазон. Предложение с минимальной закупкой 10 единиц требует отдельной проверки. Бюджет сравнивать с ценой за всю запрошенную конфигурацию только при известной единице цены.
4. **Найти кандидатов двумя путями.** Точные SKU и псевдонимы искать по ключу. Для общего запроса взять до 100 кандидатов BM25 по названию семейства и предложения, вендору, пути категории, атрибутам и описанию. Начальные веса для настройки — 8, 6, 4, 3, 2 и 1 соответственно. Сделать отдельные поля для нормализованных форм. Условия проверять на уровне предложения до окончательного отбора семейства. При слишком узкой выборке добирать кандидатов, пока есть подходящие позиции.
5. **Упорядочить и выбрать вариант.** Для точного SKU сохранять прямую ссылку. Его доступный подходящий вариант возглавляет выдачу своего семейства. Для прочих запросов учитывать совпадение фразы, сущности, категории, назначения и атрибутов. Для голого «сервер» приоритет имеют готовые машины. Запрос «почтовый сервер» ведёт в раздел ПО, а «блок питания для сервера» — в комплектующие. Текущая выбранная категория, явно заданный сегмент и история текущей mock-сессии помогают при неоднозначности. Явный текст запроса имеет приоритет над историей. Популярность из событий и mock-маржа разрешают ничью внутри близких по релевантности результатов. На этапе настройки измерить влияние каждого сигнала. Доступность и промо не заменяют релевантность.
6. **Собрать ответ.** В первой четвёрке каждое семейство занимает одно место независимо от числа редакций или лицензий. Показывать один подходящий SKU с ценой и статусом, остальные варианты раскрывать по клику. Для запроса вендора или подборки сверху идёт навигационная ссылка, под ней — семейства. Для точного артикула сохранить переход к предложению и его фактический статус. Канонический URL брать из проверенного справочника. При отсутствии адреса открывать локальную карточку со ссылками из выгрузки.

**Поиск по задаче без модели.** Для первого релиза описать в словаре 15–20 намерений закупщика, опираясь на назначение категорий. Например, «восстановить файлы после сбоя» ведёт к средствам резервного копирования, «подключаться к рабочему компьютеру из дома» — к удалённому доступу. Версионировать связи с ID категорий и проверять их на перефразировках. Для кандидата регистрировать признаки уверенности — совпадение сущности, покрытие значимых слов, подтверждённое назначение, соблюдение условий. На наборе разработки подобрать пороги отдельно для артикула, навигации и свободного текста, включая запросы без ответа. Ближайший вектор или лучший из слабых результатов сам по себе не подтверждает совпадение.

**Как собрать топ‑4.** Сначала выбрать подходящие семейства по назначению и ограничениям запроса. Если прямых семейств два, следующие два места отдать проверенным допродажам из других семейств. На карточке дополнения указать, к какому основному товару оно подходит и какое свойство проверено. Навигационная ссылка и варианты одной лицензии дополнительных мест не занимают. Счётчик прямых совпадений в сценарии «2 + 2» равен двум.

**Цена и наличие.** При выборе подходящих кандидатов сначала брать доступные предложения с положительной ценой из XML. Резерв использовать после проверки, что в той же роли и для тех же требований нет подходящего предложения первой очереди. В резерве выше позиции с известной ценой, позиции с нулевой ценой показывать при отсутствии подходящих с ценой. Явно писать «Нет в наличии по снимку» и «Цена не указана» по соответствующим полям. Для `available=false` с положительной ценой это рабочее правило команды. Обещание поставки под заказ потребовало бы отдельного подтверждения.

**Крайний случай.** Организатор привёл пример «2 + 2». Для полностью неизвестного запроса и для случая, когда даже с проверенными дополнениями не хватает четырёх семейств, команда покажет фактическое число, причину и предложение уточнить запрос. Такой случай фиксируется как неполная четвёрка. Аналоги с описанием отличий можно предложить ниже. Случайные популярные товары в выполнение требования не засчитываются.

### Где проверить пользу ML и LLM

**Эксперимент 1 — локальные эмбеддинги.** FastAPI кодирует текст моделью `intfloat/multilingual-e5-small` на CPU. До начала показа вычислить 384-мерные нормализованные векторы для 4 413 семейств ПО и 8 125 позиций электроники. Сырые векторы float32 требуют около 18,4 МиБ, дополнительно потребуется память для модели, приложения и графа поиска. Java хранит векторы в Lucene. Текст для индекса — `passage: <продукт, назначение, категория, характеристики>`, для запроса — `query: <текст>`. При поиске по задаче соединить первые 50 семантических и первые 100 лексических результатов по позициям (RRF), приведя оба списка к одному идентификатору семейства или аппаратной позиции. Сохранить контроль совместимости на уровне SKU. Для артикула и автодополнения векторный проход пропускать. [Модель, лицензия MIT и формат входа](https://huggingface.co/intfloat/multilingual-e5-small) · [Принцип RRF](https://docs.opensearch.org/latest/search-plugins/search-pipelines/score-ranker-processor/)

**Эксперимент 2 — генеративная LLM через API.** Допускать после работающего основного сценария, если ошибки на естественном языке остаются частыми. Например, «надо вернуть файлы компании после сбоя» разобрать в JSON со сферой применения и проверяемыми ограничениями. На вход — обезличенный текст и допустимый справочник. Ответ валидировать по схеме и словарю. Артикулы, цены, совместимость и товары берутся из индекса. Отдельный флаг, кэш, тайм-аут, лимит обращений, возврат локальной выдачи при сбое. Для подсказок при каждом нажатии API не вызывать. Если эксперимент не успевает пройти проверку качества и стоимости к часу 34, оставить его выключенным.

### Аналитика поисковых сессий

**Метрики для менеджера.** Доля нулевых запросов = поиски без прямых совпадений / все отправленные поиски. Уход после неудачи = завершённые неуспешные поисковые сессии без дальнейшего клика или заказа / все завершённые неуспешные поисковые сессии. Для демо считать сессию завершённой после 30 минут бездействия. Конверсия = поисковые сессии с заказом / поисковые сессии. В числитель конверсии включать сессию один раз, если у заказанного `offer_id` есть предшествующий товарный клик в этой сессии. При нескольких кликах брать `search_id` последнего клика по тому же `offer_id`. Клик по другой лицензии того же семейства такую связь не создаёт. Показывать числитель и знаменатель. Уходы и заказы не выводятся из одного факта отсутствия клика до конца сессии.

**Что делать с неудачей.** Группировать варианты написания и различать пропущенный синоним, неподходящее ранжирование, отсутствие товара в выгрузке, отсутствие в продаже и конфликт фильтров. В таблице менеджера показывать исходные примеры и проверку по полному индексу. «Нет в ассортименте» остаётся гипотезой до проверки контент-менеджером. Для «потерянных заказов» дать только сценарную оценку с допущениями — например, число неуспешных поисковых сессий × разница конверсий сопоставимых групп. Достоверный прирост заказов требует A/B-теста после подключения реальных событий. Надпись «часто покупают вместе» допустима для подтверждённых совместных покупок. В экспертных связях использовать «Подходит для…» с источником.

## 6. Как доказать качество

1. **Основной отчёт по топ‑4.** Для 8 продуктовых примеров считать FamilyHit@4 — долю запросов, где искомое семейство есть среди прямых карточек на позициях 1–4. Внутренняя цель — 8/8. Для «мтс» и «кибер бэкап» отдельно показать 2/2 правильных навигационных целей и проверить товары под ними. Отдельно по каждому сценарию записать число уникальных семейств, роли четырёх позиций и результат проверки каждой допродажи. В «2 + 2» семейства дополнений участвуют в проверке состава четвёрки, прямому запросу засчитываются только прямые совпадения. Эти метрики команды переводят уточнение организатора в воспроизводимый тест.
2. **До настройки разметить ещё 80 запросов.** Предлагаемое распределение — 15 точных SKU/версий, 15 опечаток/транслита/сленга, 15 запросов с условиями лицензирования, 15 описаний покупательских задач, 10 неоднозначных с контекстом, 10 запросов с отсутствующим или недоступным товаром. Половина — для разработки, половина — закрытый тест. Разнести варианты одного намерения/семейства по одной стороне разбиения. Оценщик, не настраивающий ранжирование, отмечает допустимые ID, недопустимые альтернативы и оценки 0/1/2 у объединённых кандидатов разных методов в перемешанном порядке. Синтетическое происхождение пометить.
3. **Сравнивать на одинаковых условиях.** A — исходный BM25, B — правила и структурированный каталог, C — B плюс E5. D с разбором через API — при запасе времени. Для A сохранять исходный порядок, отобразить SKU в семейства и отдельно показать повторы. Наряду с FamilyHit@4 измерить nDCG@4 по релевантности прямому запросу и Recall@20 для отбора кандидатов. Полезность и совместимость дополнений оценивать по их роли. Точный артикул и навигацию дополнительно проверять на первом месте. Порядок одинаково подходящих лицензий внутри семейства жюри не уточнило.
4. **Критерии для защиты.** На запросе «сервер» получить четыре разные подтверждённые модели готовых серверов. В сценарии «2 + 2» — четыре уникальных семейства, две прямые карточки и две прошедшие проверку допродажи. Прогнать также дубли одного семейства, резерв при отсутствии цены, конфликт платформ, неизвестную версию и отсутствие подходящих семейств. Уникальный доступный точный SKU идёт первым. Ноль нарушений обязательных условий среди прямых карточек и подтверждённых дополнений. Недобор вывести с причиной и учесть в отчёте. Для E5 внутренняя цель — прирост nDCG@4 на 0,05 на запросах-задачах при сохранении FamilyHit@4, корректности SKU и двух навигационных проверок.
5. **Проверить на машине показа.** Внутренние бюджеты p95 — до 150 мс для подсказок и до 500 мс для локального поиска. Прогнать смешанный набор минимум из 200 запросов при 5 параллельных клиентах, записать характеристики CPU/RAM, p50/p95, долю ошибок, холодный старт и состояние кэша. API-режим измерить отдельно, принудительно отключить внешний сервис и повторить показ. Истинную точность и бизнес-эффект после хакатона проверять на логах магазина и контролируемом эксперименте.

### По каким критериям защищать решение

На отборе организатор сначала проверяет срок и комплектность. Затем эксперты выставляют до 3 баллов по каждому из трёх критериев — соответствие задаче, убедительность демонстрации и обоснованность описания с расчётом стоимости. В финале действуют шесть критериев с равным весом из таблицы ниже, по 0–3 балла каждый. Максимум жюри — 18 баллов. Выбор партнёра для возможного пилота добавляет 6 баллов и доводит возможный итог до 24. [Положение, п. 3.5 и приложение 1](https://xn--80ancabkw0c4a.xn--p1ai/regulations/v1.html)

| Критерий из userQnA | Что показать жюри |
|---|---|
| Соответствие задаче партнёра | Полный каталог, топ‑4 разных семейств, сценарий «2 + 2» и резерв по цене |
| Корректность технической реализации | Воспроизводимые тесты по семействам, отклонение несовместимой пары, проверка при отсутствии характеристики |
| Потенциал внедрения | Вызов поискового API из независимого клиента, пример ответа и замена снимка каталога |
| Степень готовности продукта | Работающий стенд, переход к SKU, журнал запроса и восстановление после перезапуска |

Для демо используем самостоятельную компактную витрину, краткие объяснения и стабильный порядок при равных оценках. Несовместимые рекомендации исключаем, неизвестные свойства явно помечаем, отсутствие точного решения показываем вместе с обоснованными альтернативами. Включаем составные запросы, опечатки и отрицания во внутренние тесты. Предпочтения партнёра при выборе конкретного прототипа для пилота остаются открытым вопросом. ## 7. Контракт, стоимость и сдача

| Интерфейс | Минимальный контракт |
|---|---|
| `POST /v1/search` | Вход — `q`, контекст, фильтры и, при выборе подсказки, `selected_target` с полями `kind` и `target_id`. Ответ содержит `search_id`, версию снимка, основной переход `primary_target`, упорядоченный `top4[]`, число прямых семейств `direct_count` и причину недобора `shortfall_reason`. | `GET /v1/suggest?q=…` | До 6 вариантов с `kind`, `target_id` и `label`. При выборе клиент передаёт исходный текст и пару `kind`/`target_id` в `selected_target` обычного поиска. При свободном вводе клиент передаёт `q` и применённые контекст и фильтры. |
| `POST /v1/events` | Товарный клик, `add_to_cart` и позиция заказа передают фактический `offer_id`. Сохраняются сессия, время и связь с поиском, а для карточки выдачи — также семейство, роль и позиция. Повтор одного `event_id` учитывается один раз. |
| `GET /v1/analytics`, `GET /health` | Сводки с интервалом дат, источником и версией поиска. Проверка готовности возвращает состояние сервиса и дату индекса. На публичном стенде использовать только демонстрационные агрегаты. |

**Граница будущей интеграции.** Магазин вызывает тот же API из своей строки поиска. Адаптер импорта заменяется штатной выгрузкой с каноническими URL семейств. История, коммерческие сигналы и заказы поступают через отдельные адаптеры. Компонент выдачи работает при отсутствии каждого опционального источника. Для хакатона собрать клиент, сервис, импорт и SQLite в одном развёртывании. Каталог и модель подключить как версионированные артефакты. На подготовленном стенде локальные изображения-заглушки сохраняют работоспособность карточек без CDN. Обновление цен и остатков в бою будет ответственностью штатной интеграции.

**Стоимость одного запроса.** При 500 поисках в сутки и 30 днях расчётный объём — 15 000 запросов в месяц. В шаблон организатора внести фактическую стоимость сервера и хранения, долю ресурсов поиска, расходы на периодический импорт/эмбеддинги и долю обращений к API за вычетом попаданий в кэш. Средняя стоимость = (месячные затраты на инфраструктуру поиска и отдельные затраты на индексацию) / 15 000 + доля платных вызовов × средняя цена вызова. Использовать тариф провайдера и реальные средние входные/выходные токены. Не учитывать индексацию второй раз, если она уже входит в аренду сервера. Например, при условных 3 000 ₽/мес. за всё локальное размещение себестоимость составит 0,20 ₽ за поиск. Если 5% запросов дополнительно вызывают API по условным 0,40 ₽, средняя стоимость составит 0,22 ₽. Это арифметический пример, тарифы и расходы команды подставляются при сдаче.
